# 从零搭建：每次解决一个可以验证的问题

## 0. 一开始真正想解决什么

机器人连接两台路由器：一台提供蜂窝上网和调试热点，另一台连接底盘控制器和传感器。电脑连上热点后，只能进入热点自己的网段；底盘在另一个网段。与此同时，机器人自己的办公 WiFi 也能上网。

先把问题拆成三件事：调试设备访问底盘；底盘通过有线共享机器人互联网；机器人根据可达性在两个互联网出口之间切换。不要一上来桥接所有网卡，否则地址冲突、DHCP 冲突、广播影响和掉线原因会混在一起。

## 1. 先证明测试机器就是测试机器

最初先通过独立有线连接访问测试板，再检查板上真正连接的 WiFi、地址、默认路由。操作电脑连着什么 WiFi，不能代表远端测试板连着什么 WiFi。

```bash
hostname
ip -4 -br address
nmcli -f DEVICE,TYPE,STATE,CONNECTION device
iw dev wlan0 link
ip -4 route
```

期望测试设备得到热点的 `192.168.66.x/24` 地址，默认网关 `.66.1`。通过有线 SSH 操作测试板，再把 HTTP 测试显式绑定 `wlan0`，避免“实际上走了有线”的假成功。固定 IP 只有在 DHCP 不存在或需要隔离的有线管理链路时才考虑；不要随便复用其他设备的地址。

## 2. 两个网段如何互通

热点路由器需要知道：去 `.10.0/24` 找机器人 `.66.10`。机器人需要知道：`.10.0/24` 就在 eth1，并允许 IPv4 转发。底盘收到请求还必须知道如何回复。

为了保持底盘控制器原网关，机器人把调试请求源地址变成自己的 `.10.200`。底盘看到同网段来源，直接回复机器人，连接跟踪再恢复成原客户端。一个 NAT 规则不能替代前面的路由；只添加路由也不一定有正确回程。

## 3. 为什么 ping 成功，9001 却打不开

ping 只验证 ICMP；网页需要 TCP 和 HTTP。页面还可能通过另一个端口的 WebSocket 请求诊断数据。逐项验证：

```bash
ping -c 3 192.168.10.10
curl --noproxy '*' --interface wlan0 --max-time 8 \
  -sS -o /dev/null -w '%{http_code}\n' http://192.168.10.10:9001/
# 浏览器开发者工具 Network 中检查 ws://192.168.10.10:9090/。
```

如果机器人本机网页正常而热点设备失败，优先查路由器静态路由、转发计数、NAT 和返回路径；两边都失败才优先查底盘服务、线缆或地址。HTTP 200 证明页面可下载，不能独立证明界面所有业务可用。ROS 诊断读取再验证 WebSocket 101 和指定只读服务响应。

## 4. 为什么某台电脑可用，安卓却不行

路由器可能建议客户端通过 ICMP Redirect 直接找同 LAN 的机器人。有些设备接受，有些忽略。若请求经过路由器、回复却从机器人直发客户端，部分状态防火墙和客户端策略可能不接受这条不对称路径。

解决方法是记住“从热点路由器转来的连接”，对其回复用策略路由送回同一台路由器；客户端无需加静态路由或 root。项目通过连接标记、专用路由表 16600 和网关 MAC 刷新来实现。回程标记在反向 NAT 之后执行，优先级为 -90，不能照抄一个更早的钩子。

这解决的是按 IP 单播访问。跨网段自动发现、访客 WiFi 隔离、系统 VPN 拦截或浏览器要求 HTTPS 等，仍是独立条件。“任何设备”指满足这些网络条件的正常客户端，不是绕过设备自身策略。

## 5. 无线配置里有 SSID，不等于已经联网

底盘路由器曾保存办公 WiFi 名称，但诊断仍无互联网。需要看关联状态、是否有上游地址、默认路由和 DNS，不能只看网页里填了密码。旧 OpenWrt 的驱动/加密能力与现代 WPA3 热点也可能不匹配。

应区分实测事实与原因推断：保存配置但未关联是事实；只有驱动日志、加密协商结果等证据才能把原因确定为某个认证问题。后来需求明确为关闭底盘路由器无线，因此最终选择现有网线共享机器人的出口，不依赖底盘路由器的无线能力。

## 6. 不修改底盘设备网关，如何让它上网

底盘仍把外网请求交给 `.10.1`。只把底盘路由器的默认上游改成 `.10.200`，机器人对底盘外网请求做 MASQUERADE。底盘路由器两个无线均关闭。

重要检查：机器人 eth1 不能再从底盘路由器接受默认网关，否则就会出现“底盘路由器找机器人，机器人又找底盘路由器”的环路。还要固定 `.10.200`、确认它不在 DHCP 池里并做 ARP 冲突探测。保存地址、当前生效地址都要检查，避免重启后变回另一个地址。

## 7. 修复一个方向时，不要破坏另一个方向

后来新增“底盘到互联网 NAT”时，还要保留“热点到达底盘后的回复”。因此对底盘主动上网的 MASQUERADE 加 `ct direction original` 条件，避免把调试连接的回复误当成底盘主动外发流量。每次变更同时回归：热点网页、WebSocket 诊断、底盘 DNS/互联网，而不是只测试刚修的方向。

## 8. 5G 信号变好了，是否就应当一直用 5G

先确认调制解调器真的处于 5G NR 模式，再让两个出口访问相同目的 IP。记录中位数、P95、失败数和测试窗口。只比较一次 ping、比较不同 CDN 节点，或把根路径 404 当成语音 API 失败，都容易误判。

这次短时实测办公 WiFi 的时延和尾部波动更好，因此把它设为主用，5G 做备用。不会仅因为名字是“5G”就断言更快，也不会因一次波动立即切网。完整测量见 measurements.md。

## 9. 为什么仍需要应用层重连

切换 IPv4 默认路由会改变上游出口及公网 NAT 映射。既有 TCP/WebSocket 可能断开；NAT 连接跟踪也不会自动把原会话无损搬家。应用应识别断线、重连、恢复会话并避免重复播放/重复提交。

普通应用、内核和语音平台不具备端到端 MPTCP 支持时，仅把两张网卡都连上不会让一个会话聚合两路带宽。语音更关注低时延、低抖动、稳定可达和可控的重连，带宽相加通常不是第一优先级。

## 10. 另外两类问题不要混为网络故障

远程桌面里点击浏览器却启动不了，应检查进程、显示会话和启动日志；浏览器尚未启动时，不能归因于底盘网页。WiFi 扫描反复弹认证框，通常是桌面扫描请求与 Polkit 会话授权问题；应限制到所需用户和扫描动作，不能为了消除弹窗而全局取消认证。本工具箱不自动改桌面或 Polkit 设置。

## 实验记录模板

每次只改一类变量，记录：时间/时区、设备身份、当前地址与路由、假设、修改前结果、具体命令、修改后结果、是否恢复、未证明的事项。保留原始报告在私有目录；公开时只发布去标识的结论。一次未重启验收通过，不能写成“重启后已验证”。
